# Playbooks

This is where I document how I actually work.

Not theory. Not best practices copied from somewhere else.  
Just methods that come from real projects—what worked, what didn’t, and what I kept.

---

## Why playbooks

Good documentation doesn’t start with writing.

It starts with:
- getting the right information
- asking the right questions
- understanding how the system is actually used

Most problems in documentation are not writing problems.  
They’re process problems.

Playbooks are how I solve them.

---

## What you’ll find here

Each playbook focuses on a specific part of the workflow:

- how I run SME interviews  
- how I extract usable information from incomplete inputs  
- how I validate documentation before it goes out  

They are designed to be:
- practical  
- repeatable  
- usable in real projects  

---

## How to use this

If you’re:
- a developer → this shows how I’ll work with you  
- a product manager → this shows how I reduce back-and-forth  
- a team → this shows how documentation can be delivered without chaos  

---

## What this leads to

Clear documentation is not an accident.

It’s the result of:
- structured inputs  
- focused conversations  
- and validation before publishing  

That’s what these playbooks are built for.
